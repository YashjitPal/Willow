# apps/android

Willow for Android: a React Native (Expo) shell that shows the Willow running on
the user's PC in a full-screen WebView, and lets the PC's agents use the phone.
Nothing of Willow runs on the phone. Two raw TCP tunnels put the PC's servers on
the phone's loopback, so the pages run at `http://localhost:41861/` (Willow) and
`http://localhost:41860/` (the agents' T3 Code server): secure contexts
(`crypto.subtle`, `getUserMedia`) whose origins, and so whose storage, stay the
same when the PC's address changes.

Its own npm package (Expo SDK 57, React Native 0.86, new architecture only),
outside the root workspace and tsconfig. Nothing outside `apps/android` depends
on it; pages reach it only through `window.__WILLOW_ANDROID__` (the contract
below). The other ends:

- **The PC side** is the agents' server: `vendor/t3code/apps/server/src/willow/mobile.ts`
  serves Willow's page to paired phones, `folder.ts` serves them the PC's Willow folder,
  and `phone.ts` routes the agents' `phone_*` tools.
- **Willow's page side** is `platform/core/src/android-bridge.ts`. It covers the agents
  tab's sign-in, the companion relay and the phone-tool relay. `android-folder.ts` beside
  it hands Willow's storage the PC's folder (see Willow's data). The page also has agent
  rows in the sidebar, and Back closes an agent tab (`features/harness/src/harness-android.ts`).

## How it works

1. **Connect.** With Network access on, the agents tab's Settings > Connections
   shows T3 Code's pairing link `http://<host>:<agentsPort>/pair#token=<credential>`
   and its QR code. The phone scans or pastes it (the token is read as
   `URLSearchParams` would, from the hash, else the query), then asks
   `GET http://<host>:<agentsPort>/.well-known/willow/mobile` (public) for
   `{"version":1,"willowPort":<n>,"agentsPort":<n>}`. An `https://` link (Tailscale
   Serve) is asked over https. The tunnels still go to the server's own plain port,
   the answer's `agentsPort`, because a TCP tunnel can't carry TLS to an
   `http://localhost` page. That port must answer too, so Network access must be on.
2. **Tunnels.** `127.0.0.1:41860 → host:agentsPort` and
   `127.0.0.1:41861 → host:willowPort`. The ports are fixed: the session cookie,
   and what Willow's page keeps in the WebView's localStorage and IndexedDB while
   it runs, belong to these origins.
3. **Pair.** `{host, agentsPort, willowPort}` is saved (AsyncStorage, never the
   token) and the WebView opens `http://localhost:41860/pair#token=…`. The agents'
   client pairs and sets its session cookie for `localhost` (cookies ignore ports,
   so it covers 41861 too). When it leaves `/pair`, or after 15 s, a new WebView
   opens `http://localhost:41861/`, so Back never returns to the pairing page.
4. **Later launches** probe the saved PC, reopen the tunnels (picking up a new
   Willow port) and load Willow directly. If the PC can't be reached, the Connect
   screen says why and offers to try it again.

**The tunnels** (`TcpTunnel.kt`) move bytes and never parse them, so HTTP,
Server-Sent Events and WebSockets pass unchanged. `start` listens on
`127.0.0.1:<localPort>` with `SO_REUSEADDR`; each accepted socket gets its own
socket to the PC (10 s connect timeout, `TCP_NODELAY`, keep-alive) and two pump
threads until either side closes, a half-close passed on. `start` on a port that
is already listening, with another remote, retargets it and drops its open
connections. Errors reject with `ERR_TUNNEL_PORT`, `ERR_TUNNEL_HOST` or
`ERR_TUNNEL_BIND`. Tunnels live as long as the app's process.

**The WebView** has JavaScript, DOM storage, shared and third-party cookies, file
access and `<input type=file>` (react-native-webview's chooser: files or the
camera), autoplay, geolocation, `originWhitelist ['*']`, no multiple windows, no
pull-to-refresh, no overscroll, and the theme's background. `localhost`,
`127.0.0.1` and `*.localhost` (Spark's browsed sites) load in place, `target=_blank`
included; any other `http(s)`, `mailto:` and `tel:` go to the system. Back walks the
WebView's history, then leaves the app. A 2px bar shows load progress. A page that
can't be reached gives "Can't reach Willow on your PC" with Retry (probe, tunnels,
reload) and Connect another PC. The settings button (three dots) is only on the
Connect screen and that error view; pages open the sheet through the bridge. A
crashed renderer gets a new WebView. The user agent ends in `WillowAndroid/<version>`.

**Willow's data** is the PC's. Willow's page has no folder picker on the phone:
`platform/core/src/android-folder.ts` hands Willow's storage the PC's Willow folder as
its local folder, a File System Access handle over `/api/willow/folder` on the Willow
origin. Willow's sync engine reads and writes it as on the PC (chats, settings with the
API keys, dots, projects, gems, notebooks), so a change on either side shows on the
other within a pass of it, about 3 s. The handle asks for the folder's version at most
once a second, lists again only after it changes, and keeps recently read files (up to
64 MB, files to 8 MB) until then. The page's working copies in localStorage and
IndexedDB last until Disconnect.

**Disconnect this PC** leaves Willow's page first, then stops the tunnels, forgets
the PC and erases what the WebView keeps: localStorage, IndexedDB and the rest of
its web storage (`WebStorage.deleteAllData`), its cache and its cookies, natively
(react-native-webview has no API for them). Willow's data stays on the PC, so
connecting again finds it as it was.

## The page bridge (contract)

On every document of the two origins, before the page's own scripts:

```js
window.__WILLOW_ANDROID__ = {
  version: 1,
  agentsOrigin: 'http://localhost:41860',
  tools: [/* TOOL_NAMES, [] while agent access is off */],
  listeners: [],              // kept when the object already exists
  receive(message) {},        // calls each listener with message
  post(message) {},           // window.ReactNativeWebView.postMessage(JSON.stringify(message))
  openSettings() {},          // post({ kind: 'open-settings' })
};
```

Page to native, through `post`:

- `{kind:'phone-call', id, tool, args}`: runs the tool and answers
  `{kind:'phone-result', id, ok:true, result}` or `{kind:'phone-result', id, ok:false, error}`.
- `{kind:'pairing-required'}`: the Connect screen, asking to pair again.
- `{kind:'open-settings'}`: the settings sheet.
- `{kind:'open-external', url}`: the system browser, `http`/`https` only.
- `{kind:'notify', title, body?, tag?}`: Willow's own notification, for example an agent's
  turn finishing. It comes from `showNotification` in Willow's desktop-bridge.ts. Agent access
  doesn't gate it, and one with a `tag` replaces the last with that tag.

Native to page: `injectJavaScript("window.__WILLOW_ANDROID__ && window.__WILLOW_ANDROID__.receive(" + JSON.stringify(message) + "); true;")`.
Besides `phone-result` it sends `{kind:'tools-changed', tools}` (after updating
`tools`) when the agent-access switch moves, so listeners ignore kinds they don't
know.

The script is ES5 and idempotent. react-native-webview runs
`injectedJavaScriptBeforeContentLoaded` from `onPageStarted` on Android, which can
lose the race with a page's first scripts, so the same script is also a real
document-start script (`WebViewCompat.addDocumentStartJavaScript`, limited to the
two origins, installed before the first load) and runs once more at load end.
Messages count only from frames on the two origins: `window.ReactNativeWebView`
exists in every frame, Spark's browsed sites included.

## Phone tools

`src/phoneTools.ts`. Arguments are validated; every tool rejects with
`Agent access is turned off on this phone` while the switch is off (default on).

| Tool | Arguments | Result |
| --- | --- | --- |
| `phone_status` | none | `{model, manufacturer, osName, osVersion, battery: {level, state}, network: {type, connected}}` |
| `phone_location` | `accuracy?: 'balanced' \| 'high'` | `{latitude, longitude, accuracy, altitude, timestamp}` |
| `phone_notify` | `title`, `body?` | `{shown: true}` |
| `phone_vibrate` | `pattern?: 'light' \| 'medium' \| 'heavy' \| 'success' \| 'warning' \| 'error'` | `{done: true}` |
| `phone_open_url` | `url` (http/https) | `{opened}` |
| `phone_clipboard_set` | `text` | `{done: true}` |
| `phone_photo` | `maxSize?` (64 to 4096, default 1024) | `{mimeType: 'image/jpeg', base64, width, height}` |

- `battery.level` is 0 to 1, or `null` when unknown; `state` is `charging`, `full`,
  `unplugged` or `unknown`.
- Location asks for foreground permission when it may; a fix taking over 20 s falls
  back to the last known position (up to 10 minutes old).
- Notifications ask for permission (Android 13+) and post on an "Agents" channel.
- A photo first asks "An agent wants to take a photo with your camera. Allow?"
  (Deny: `The phone owner declined`), then opens the camera; the JPEG (quality 0.7)
  is scaled so its long edge is at most `maxSize`. One at a time.

## Build and install

`npm install` in `apps/android` (never at the repository root), a JDK 17+
(Android Studio's `jbr` is used when present) and the Android SDK
(`%LOCALAPPDATA%\Android\Sdk`, or `ANDROID_HOME`).

```powershell
node apps/android/scripts/build-apk.mjs           # apps/android/dist/Willow.apk
node apps/android/scripts/build-apk.mjs --clean   # regenerate android/ first
adb install -r apps/android/dist/Willow.apk
npx tsc --noEmit                                  # in apps/android
```

The script sets `JAVA_HOME` and `ANDROID_HOME`, runs `expo prebuild --platform
android --no-clean` (Expo SDK 57 cleans by default), installs with sdkmanager the SDK
packages the build asks for (platform, build tools and NDK from React Native's
version catalog, CMake 3.22.1), runs `gradlew assembleRelease --no-daemon` and copies
the APK. ABIs: `arm64-v8a` (phones) and `x86_64` (emulators). Release builds are
signed with the template's debug keystore, the same on every prebuild, so a new build
installs over the last. Fine for sideloading, not for the Play Store. The first build
compiles C++ for both ABIs and takes a while; after a JS or Kotlin change, about 3
minutes.

Two workarounds, both for Windows:

- **Gradle's download.** The wrapper's Java client tries only the first address it
  resolves, and GitHub, where Gradle is hosted, can resolve to one that doesn't answer.
  The script downloads the distribution itself (checked against Gradle's published
  SHA-256) into `.cache/gradle/` and points the wrapper at that file.
- **A space in the SDK's path** (`C:\Users\First Last\...`). CMake writes the
  compiler's path in its 8.3 form, and `clang++.exe` called as `CLANG_~1.EXE` takes
  itself for the C driver: every native library fails to link with undefined libc++
  symbols. `scripts/clang-driver-mode.gradle` adds `--driver-mode=g++` to every
  module's `cppFlags`. A native build configured without it keeps failing until its
  `.cxx` folder (`android/app/.cxx`, `node_modules/expo-modules-core/android/.cxx`)
  is deleted.

**Trying it without Willow**: `node apps/android/scripts/mock-pc.mjs` answers as the
PC on 127.0.0.1:47100 (agents) and :47101 (Willow); in an emulator, pair with
`http://10.0.2.2:47100/pair#token=test`. Its page shows the bridge, the session cookie
crossing ports, SSE and a WebSocket through the tunnel, and has buttons for the tools.
React Native pauses JS timers while its activity isn't in the foreground, so on an
emulator that booted to its lock screen nothing happens until
`adb shell wm dismiss-keyguard`. `adb shell pm clear com.willow.android` starts over.

## Verified

On 2026-10-09, the release APK on an Android 14 emulator (the SDK's `android-desktop`
x86_64 image) against `scripts/mock-pc.mjs`: launch and the Connect screen; a pasted
link's probe, tunnels, pairing and hand-off to Willow; the session cookie across the
two ports; SSE and a WebSocket through the tunnels; the bridge (version, origin, tools)
and a `phone_status` round trip; `open-settings`; `tools-changed` and the "turned off"
rejection when agent access is switched off; reconnecting on a later launch; the
Connect screen's error when the PC is down; Disconnect this PC.

The same day, the release APK on a phone-sized (720×1520) Android 14 emulator against
the real backend: the agents' server run from source with its phone listener, and a
stand-in companion. Checked:

- a pasted link paired the phone and Willow loaded through the tunnels (the
  phone home, its model pill and composer);
- the drawer's agent rows appeared, which proves the bridge;
- Codex's tab loaded from `http://localhost:41860/`;
- one Back closed it again;
- with the server serving a stand-in Willow folder, a chat made on the computer showed
  on the phone and opened, and one removed on the phone went to the folder's
  `Recycle Bin` on the computer;
- Disconnect this PC emptied the WebView's IndexedDB and localStorage (checked as root
  in the app's `app_webview` folder).

Not yet: QR scanning, location, notifications, vibration, clipboard, photos and links
on a real phone.

## Known limits

- Google refuses its sign-in inside an embedded WebView, and popups go to the
  system browser, whose cookies the app can't see: signing in with Google from the
  phone doesn't work.
- Willow on the phone works only while it reaches the PC: its data is the PC's folder,
  with nothing kept for offline use.
- Agents reach the phone only while the app is open: no foreground service, and
  Android may stop the app in the background.
- Plain HTTP on the local network: the PC's servers have no TLS.
- `mediaCapturePermissionGrantType` is iOS-only in react-native-webview. On Android,
  once the app holds the permission, the WebView grants camera, microphone and
  geolocation requests from any origin that reaches it. The browser's permissions
  policy (default `self`) stops a cross-origin frame from asking at all unless its
  parent allows it. Willow allows it only for the agents' page frame, and only for
  the camera and microphone.
- Libraries add permissions to those in `app.json`: expo-notifications brings boot,
  wake lock, Firebase push and launcher badge permissions. `SYSTEM_ALERT_WINDOW`, from
  Expo's template, is blocked.
